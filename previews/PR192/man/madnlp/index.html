MadNLP

The MadNLP binding of SparseDirectSolver.jl lives in MadNLP.jl (version 0.12 and later), not in this package: the linear solver SDSSolver is a marker exported by MadCoreGPU, implemented by its extension MadCoreGPUSDSExt, which loads with SparseDirectSolver.jl. The extension is a shell over KKTSolver (KKT solver), the MadNLP-independent front end of this package. SparseDirectSolver.jl 0.3 shipped a MadNLP extension of its own (for MadNLP 0.11); it was removed in 0.4.0.

Using it

SDSSolver is the default sparse linear solver of MadNLP's AMD, Intel and Apple entry points, which load SparseDirectSolver.jl themselves:

using rocMadNLP                       # AMD; oneMadNLP for Intel, mtlMadNLP for Apple
using ExaModels, AMDGPU

nlp = ExaModel(model; backend = ROCBackend())   # a JuMP model, loaded on the GPU
result = madnlp(nlp)                            # SDSSolver is the default

The NVIDIA entry point cuMadNLP defaults to cuDSS; with SparseDirectSolver.jl loaded, SDSSolver is selected explicitly:

using cuMadNLP, SparseDirectSolver    # SparseDirectSolver loads MadCoreGPUSDSExt
using ExaModels, CUDA
const SDSSolver = cuMadNLP.MadCoreGPU.SDSSolver

nlp = ExaModel(model; backend = CUDABackend())
result = madnlp(nlp; linear_solver = SDSSolver)

The installation of the entry points (some are not registered yet) and the choice of the KKT system and preset are described in MadNLP's documentation. MadNLP's default preset on a GPU asks for an L D Lᵀ without pivoting (sds_factorization = :ldl, sds_pivoting = :none) with a pivot bound (sds_pivot_epsilon), the counterpart of cuDSS's pivot epsilon in the same preset. The binding reads MadNLP's lower-triangular KKT matrix (a device CSC matrix) as the CSR of its upper triangle, exactly as the cuDSS binding does; Float32 and Float64 are supported (Float32 only on Metal and on Intel GPUs without Float64).

Options

The sds_* options belong to MadNLP and are documented there; they are passed as keywords of madnlp. Each one maps to a keyword of KKTSolver:

MadNLP optionKKTSolver keywordmeaning
sds_factorizationfactorization:cholesky ("SPD") or :ldl ("S", inertia from the signs of D)
sds_pivotingpivoting:ldl only: :none (pivot order of the analysis) or :bk (in-front Bunch–Kaufman, stock pipeline, Symmetric indefinite systems)
sds_pivot_thresholdpivot_threshold:bk only: the pivot_threshold of the acceptance test (nothing keeps the package default 0.01; cuDSS's default is 1.0)
sds_pivot_epsilonpivot_epsilonthe pivot_epsilon below which a pivot is replaced; for :ldl it selects the stock pipeline, since the fused L D Lᵀ replaces no pivot (fused = true refuses it)
sds_reorderingreorderingthe reordering_alg of the analysis: "algo4" nested dissection (METIS), "algo3" AMD, "default" the cost-model choice (Parameters)
sds_user_permuser_perma 1-based permutation of length n that replaces the reordering, for instance a cached one; every solver instance otherwise recomputes its ordering
sds_tuningtuningan SDSTuning bundle of performance settings; nothing selects the measured per-architecture defaults of default_tuning
sds_fusedfusedtrue the fused pipeline, false the stock one, nothing the default of the backend

The sizes of the primal and dual blocks, which MadNLP's KKT system knows, give the pivot_sign of KKTSolver (1 for the primal and -1 for the dual rows): the sign a replaced pivot takes in a stock L D Lᵀ without pivoting. Like pivot_epsilon, it selects the stock pipeline for :ldl.

KKTSolver has two keywords for the setting of MadNLP's cuDSS preset (an L D Lᵀ with matching and pivot epsilon, analyzed on the first KKT values), whatever MadNLP's binding exposes of them:

  • matching (default "none"): the "matching_alg" of the analysis, :ldl only, on the stock pipeline (fused = true refuses it). With "algo5" and "algo6" the 2×2 pivot pairs of the ordering come from the cycles of the scaled symmetric matching, with pivoting = :none as with :bk.
  • deferred_analysis (default false): the constructor checks the options but neither analyzes nor factorizes; the first factorize! analyzes the values present then (the counterpart of the cuDSS binding's deferred analysis), the later ones refactorize.

Without matching, with pivoting = :bk the 2×2 pivot pairs of the "S" analysis are chosen from the values present in the KKT matrix at the analysis (see Pivot pairs under Parameters); with :none the pairs are off, since a factorization without pivoting never consumes them.

What runs underneath

KKTSolver chooses the pipeline; SparseDirectSolver.pipeline tells which one runs.

  • Fused pipeline (the default for pivoting = :none on CUDA, AMDGPU and oneAPI, the backends with forward progress between workgroups, unless an L D Lᵀ asks for matching, pivot_epsilon or pivot_sign): the inner solver is a FusedSolver over the symbolic analysis of a regular DirectSolver. One dependency-counter kernel per refactorization covers the whole elimination tree (the wide root fronts of an LDLᵀ always inside the kernel, since a saddle-point root mixes pivot signs; those of a Cholesky inside the kernel or on the vendor potrf path, chosen by the tuning), the inverses of the diagonal blocks of the fronts are computed after each factorization, and the solve is a partitioned-inverse sweep, one dependency-counter kernel per direction. This is the path that cholesky_fused measures on the Performance page.
  • Stock pipeline (pivoting = :bk, fused = false, an L D Lᵀ with matching, pivot_epsilon or pivot_sign, and every factorization on the KernelAbstractions CPU backend and on Metal): the inner solver is a DirectSolver with the same tuning, driven through refactorize! and solve! at the level-batched speed of execute!. Cholesky, L D Lᵀ without pivoting and Bunch–Kaufman L D Lᵀ all run on it.

The inertia after each factorization comes from SparseDirectSolver.inertia: for :ldl from the signs of D (2×2 blocks included), for :cholesky (n, 0, 0). It is valid when getparam(K, "info") is 0; MadNLP's binding reports a failed factorization as an indefinite inertia, so that MadNLP regularizes and factorizes again.

Tuning

Every performance knob of the fused pipeline lives in one immutable bundle, so a platform's tuning is a single value; how each field was measured and the per-architecture champions are in bench/ARCH-TUNING.md.

using SparseDirectSolver: SDSTuning
tuning = SDSTuning(; nd_nseps = 4)   # lower fill, ~2× the reordering time
madnlp(nlp; sds_tuning = tuning)

The bundle and its defaults are documented on the Fused pipeline page.
