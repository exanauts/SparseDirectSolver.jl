Fused pipeline

FusedSolver runs the fused factorization and partitioned-inverse solve of SparseDirectSolver.Fused (src/fused.jl) behind the verbs of DirectSolver: the same execute! phases, setparam!, getparam and update!, for one right-hand side, on a GPU backend, for "SPD" and no-pivot "S" real matrices. It is the inner solver of the MadNLP extension's SDSSolver (MadNLP); Performance says when to use it.

using SparseDirectSolver, CUDA, CUDA.CUSPARSE

Ad = CuSparseMatrixCSR(tril(A))       # A: SPD, on the host
F = FusedSolver(Ad, "SPD", 'L')
analyze!(F)                           # ordering, symbolic analysis, the fused plans
factorize!(F)                         # the fused factorization
bd = CuVector(b)
x = F \ bd                            # partitioned-inverse solve
getparam(F, "info")                   # 0 on success

Ad.nzVal .*= 2                        # new values in the same buffer (the IPM loop)
refactorize!(F)
solve!(F, x, bd)
SparseDirectSolver.Fused.FusedSolver — Type
FusedSolver(A, structure, view; tuning = nothing, index = 'O')
FusedSolver(rowptr, colval, nzval, structure, view; tuning = nothing, index = 'O')

The fused pipeline of SparseDirectSolver.Fused (dependency-counter factorization mega-kernel and partitioned-inverse solve, the SDSSolver path of the MadNLP extension) as an AbstractDirectSolver, driven by the same verbs as DirectSolver: execute!, analyze!, factorize!, refactorize!, solve!, setparam!, getparam, update!, ldiv! and \ for one right-hand side. A is anything DirectSolver accepts with these arguments (a CSR, CuSparseMatrixCSR/CuSparseMatrixCSC, ROCSparseMatrixCSR, …) on a GPU backend; the values alias the caller's nzval, so writing new values into it and calling refactorize! is the interior-point loop (update! with the same pattern is forwarded).

structure is "SPD" (fused Cholesky) or "S" (fused LDLᵀ without pivoting: pivot_type = 'N', pivot_pairs = "none"). tuning is an SDSTuning, nothing meaning default_tuning(backend), resolved by resolve_tuning; the constructor applies it to the inner DirectSolver (amalgamation, regime-C width and rows, subtree parallelism and budgets, reordering_alg = "algo4", nd_nseps, nd_seed). The inner solver is the field inner.

Phases (execute!(phase, F, X, B; asynchronous = true)):

  • "reordering", "symbolic_factorization", "analysis": the inner solver's phase; the symbolic part then factorizes and solves once with the inner solver (stock kernels, it sizes the solve workspace) and builds the fused factorization plan, the per-front inverses and the fused solve segments. X and B are not used.
  • "factorization", "refactorization" (needs a previous "factorization"): the fused factorization of the current values, then the inverses of the diagonal blocks; sets "info" (0, or the original column of the first failed pivot: a non-positive Cholesky pivot, or for "S" a zero or non-finite pivot). A failed factorization does not throw. "S" factors its wide fronts in the fused kernel under either wides strategy (a front's pivots may take both signs), so the in-kernel wide-front limit applies to it on every part: a front with more than 1023 · 32 rows below a panel raises NotSupportedError at analysis.
  • "solve": X = A⁻¹ B with the partitioned-inverse solve, for a vector (or an n × 1 matrix) on the solver's backend; X === B is allowed.

setparam! accepts "user_perm", "reordering_alg", "nd_nseps", "nd_seed" and "pivot_epsilon" (the Cholesky pivot epsilon; the fused LDLᵀ factors with epsilon 0), all read by the next analysis. getparam returns "info", "inertia" ((npos, nneg); "SPD": the positive pivots and 0; "S": the counts of positive and negative entries of D), "npivots" (0 for "S": the fused LDLᵀ perturbs no pivot), the analysis data "perm_reorder_row", "perm_reorder_col", "perm_row", "perm_col", "lu_nnz", "flops", "nsuperpanels", "memory_estimates" of the inner solver, and the configuration parameters.

Everything the pipeline does not do raises NotSupportedError, at construction or in the phase, never a silent switch to the stock path: the KernelAbstractions CPU() backend (the dependency-counter kernels spin on resident workgroups, which the CPU backend runs one after another), complex element types, the structures "HPD", "H" and "G", a uniform batch (nbatch > 1), nrhs > 1, a transposed solve (solve_mode ≠ 0), the solve sub-phases ("solve_fwd_perm" … "solve_refinement", the Schur phases), Schur mode, matching_alg ≠ "default", ir_n_steps > 0, deterministic_mode = 1 (the concurrent extend-add sums in arrival order), a factor_precision other than the working precision, "S" with pivot_type ≠ 'N', a matrix without a front of width ≤ 256 for the fused solve, and every setparam! name not listed above. The options of the inner solver are checked again at the analysis. DirectSolver remains the general solver.

The performance knobs of the pipeline live in one bundle, a platform's tuning being a single value; how each field was measured and the per-architecture champions are in bench/ARCH-TUNING.md. default_tuning gives oneAPI, Metal and any other backend that reports no CUDA thread count per multiprocessor the AMD profile.

SparseDirectSolver.Fused.SDSTuning — Type
SDSTuning

Every performance knob of the fused pipeline in one immutable bundle, so a platform's tuning is a single value (see bench/ARCH-TUNING.md for how each field was measured and the per-architecture champions). All fields are runtime parameters — no environment variables, no recompilation.

SparseDirectSolver.Fused.default_tuning — Function
default_tuning(backend) -> SDSTuning

The measured per-architecture defaults — the single place they live. 2048-threads/SM NVIDIA parts (sm70/80/90): host wides, 16K budgets. 1536-thread parts (sm86/89, Blackwell workstation): merged wides, 8K budgets. AMD (gfx906-measured): merged, 8K, workgroup 256, spin cap 16. A backend without a CUDA resident-thread count (max_threads_per_multiprocessor returns 0: AMDGPU, oneAPI, Metal, the CPU backend, anything but CUDA) gets this AMD profile.

SparseDirectSolver.Fused.resolve_tuning — Function
resolve_tuning(t::SDSTuning, backend) -> SDSTuning

t with wides = :auto replaced by the wide-front strategy of default_tuning(backend); any other t is returned as is.
